# CodexWebProxyApi

[简体中文](README.md) | [English](README_EN.md)

Let your local Codex use ChatGPT Web through the ordinary Chrome profile where you are already signed in. In the experimental Agent mode, structured tool requests generated by the web model are safely returned to Codex for local execution.

> [!IMPORTANT]
> This is an unofficial experimental project and is neither affiliated with nor supported by OpenAI. It depends on the ChatGPT Web DOM and may stop working because of website updates, account restrictions, authentication state, or risk controls. Make sure your usage complies with applicable terms and organizational policies. Use a supported official API in production.

## What problem does it solve?

Codex natively uses the Responses protocol, while a ChatGPT session in a browser is not a Responses API. This project provides a minimal local adapter:

```text
Codex CLI / Desktop
        │ Responses JSON / SSE
        ▼
http://127.0.0.1:4318/v1
        │
        ├── Native Codex models ──► Official Codex backend (transparent proxy)
        │
        └── chatgpt-web/*
                 │ WebSocket ws://127.0.0.1:4319
                 ▼
          Manifest V3 extension
                 │ Current Chrome sign-in state
                 ▼
             ChatGPT Web
```

The entire chain listens on loopback only. It does not require a public IP address, an MCP tunnel, Electron, CDP injection, or cookie export.

## Features

### Two web-backed models

| Model | Intended use | Local tools |
| --- | --- | --- |
| `chatgpt-web/browser` | Regular text Q&A, analysis, and writing | Unavailable |
| `chatgpt-web/agent` | Codex Agent workflows | Experimental function/custom tool support |

`chatgpt-web/agent` never executes shell commands directly. The web model can only return a structured tool request containing a random nonce. The local provider validates the nonce, tool number, and JSON arguments, then returns a standard Responses `function_call` to Codex. Codex remains responsible for deciding whether and how to run it, including sandboxing.

### Responses compatibility layer

- `/v1/models` preserves the native model list and adds the two web-backed models.
- `/v1/responses` supports both streaming SSE and non-streaming Responses JSON.
- Supports `previous_response_id` and Codex's stateless tool-history replay.
- Native models continue using existing Codex authentication and are transparently forwarded to the official backend.
- Supports zstd-compressed requests from Codex.

### Reliable browser tool loop

- Reuses the same ChatGPT conversation after a tool call instead of refreshing the page at every step.
- Sends only new tool results on subsequent turns rather than replaying the full Codex request.
- Sends a recovery prompt only when browser conversation state has actually been lost.
- Requires Agent replies to contain the complete JSON envelope for the current nonce; pauses in streamed output are not mistaken for completion.
- A background run lock prevents concurrent retries from refreshing the provider tab while a response is being generated.
- Binds each request to exactly one new assistant reply through a logical turn identity.

### Minimized context

The content sent to ChatGPT Web excludes:

- Codex host developer/system instructions;
- skills, permissions, plugin, environment, and application metadata;
- duplicate Responses Lite tool metadata;
- full history that already exists in the same browser conversation.

Tool descriptions and JSON Schemas are also compacted to reduce prompt size in the web UI.

### Recoverable configuration

The CLI updates the user-level `~/.codex/config.toml` transactionally and stores the original bytes in a private state directory. `restore` checks whether another program changed the configuration before restoring it, so newer user changes are not overwritten.

## Requirements

- Node.js `22.15` or later;
- Google Chrome `116` or later;
- a working Codex CLI or Codex Desktop installation;
- access to `https://chatgpt.com` from a regular signed-in Chrome profile;
- macOS or Linux. Windows has not yet been fully validated; compatibility contributions are welcome.

## Quick start

### 1. Clone the repository and install dependencies

```bash
git clone https://github.com/pachi-33/CodexWebProxyApi.git
cd CodexWebProxyApi
npm ci
```

### 2. Load the Chrome extension

Print the extension directory first:

```bash
node src/cli.mjs extension
```

Then, in the Chrome profile you use every day:

1. Open `chrome://extensions`.
2. Enable **Developer mode** in the top-right corner.
3. Click **Load unpacked**.
4. Select the repository's `chrome-extension/` directory.
5. Open `https://chatgpt.com` and confirm that you are signed in and can send a message normally.

The extension requests only `tabs`, `https://chatgpt.com/*`, and local loopback permissions. It runs directly in the current Chrome profile, so it naturally uses your existing signed-in session. It does not read, copy, or export cookies.

### 3. Start the local provider

```bash
npm start
```

Keep this terminal running. Normal output looks like this:

```text
Provider listening at http://127.0.0.1:4318/v1
Waiting for normal Chrome extension at ws://127.0.0.1:4319
```

Check the connection:

```bash
npm run status
curl http://127.0.0.1:4318/healthz
```

`extension_connected` should be `true` in the health response.

### 4. Connect Codex

In another terminal, run:

```bash
node src/cli.mjs install
```

This command first checks provider health and then writes the following entry to the user-level `~/.codex/config.toml`:

```toml
openai_base_url = "http://127.0.0.1:4318/v1"
```

This follows the Codex custom-provider routing mechanism for Responses. A project-level `.codex/config.toml` is not appropriate for provider routing. The CLI does not change the approval policy, sandbox configuration, or default model.

Restart Codex, then choose one of these entries in the model selector:

- `ChatGPT Web (Browser)` for web-backed text conversations without local tools;
- `ChatGPT Web (Agent, experimental)` to let the web model request Codex local tools.

### 5. Verify the setup

Browser mode:

```text
Reply exactly: WEBGPT READY
```

Agent mode:

```text
Use the read-only shell tool to run pwd, then tell me the current directory.
```

Under normal operation, Chrome keeps one dedicated Temporary Chat tab. Multiple tool calls within one Agent task continue in the same conversation.

## Restore the original Codex configuration

After stopping the provider, run:

```bash
node src/cli.mjs restore
```

If `openai_base_url` already existed before installation, the CLI refuses to replace it by default. Use the following only when you intend to replace that route:

```bash
node src/cli.mjs install --replace-existing-route
```

`restore` restores the exact configuration from before installation. If another program has modified the configuration since installation, it refuses to overwrite those changes and asks you to resolve the conflict manually.

## CLI commands

```text
codex-chatgpt-web extension
codex-chatgpt-web login [--transport extension|playwright]
codex-chatgpt-web serve [--port 4318] [--transport extension|playwright]
codex-chatgpt-web install [--port 4318] [--replace-existing-route]
codex-chatgpt-web status [--port 4318]
codex-chatgpt-web restore
```

When running directly from the source tree, replace `codex-chatgpt-web` with `node src/cli.mjs`.

Optional arguments:

- `serve --timeout SECONDS` changes how long the provider waits for a ChatGPT reply; the default is 600 seconds;
- `serve --port PORT` changes the HTTP provider port;
- `login/serve --transport playwright` uses an isolated Playwright profile;
- `--chrome PATH` and `--profile DIR` apply only to the Playwright fallback.

## Playwright fallback

If the normal Chrome extension is unavailable, use an isolated profile:

```bash
node src/cli.mjs login --transport playwright
node src/cli.mjs serve --transport playwright
```

Do not point Playwright at the user-data directory of a regular Chrome instance that is already running. Chrome profiles are exclusively locked, abnormal termination can damage preferences or cookie data, and automation launch characteristics are more likely to trigger website risk controls.

## Security design

- The HTTP provider is fixed to `127.0.0.1`; non-loopback addresses are rejected.
- The WebSocket bridge is fixed to `127.0.0.1` and accepts only a `chrome-extension://` Origin.
- Node.js does not read or store Chrome cookies.
- The native Codex bearer token is transparently forwarded in memory and is never written to logs or disk.
- Webpage text is never executed directly as shell code.
- Agent tool calls must pass random-nonce, declared-tool, and JSON-argument validation.
- Actual local tool calls are executed by Codex and therefore remain subject to its sandbox and approval policies.
- Configuration backups are stored in `~/.codex-chatgpt-web-minimal/` with permissions restricted to the current user.

Public deployment, port forwarding, and reverse proxying are outside this security model. Do not expose ports `4318` or `4319` to your LAN or the public internet.

## Data flow and privacy

When you select a web-backed model, the filtered user conversation, tool definitions, and tool output are displayed in ChatGPT Web and sent to the ChatGPT service. When you select a native Codex model, the local proxy transparently forwards the request to the Codex backend.

Before using the project, consider whether your code, file contents, terminal output, and other context are appropriate to send to your ChatGPT account. Company-managed devices and organization accounts may also be subject to administrator network, browser, and data-retention policies.

## Known limitations

- The ChatGPT Web DOM is not a stable API, so selectors can change without notice.
- Expired sign-in state, account limits, risk controls, network proxies, and webpage errors can all cause requests to fail.
- `chatgpt-web/agent` is experimental and should not run high-risk commands unattended.
- Structured output, web-model compaction, image input/output, and multi-agent workflows are not currently supported.
- Continuation state lives in the current Node.js process; old `previous_response_id` values cannot be resumed after a restart.
- Only one web request is processed at a time to prevent multiple tasks from competing for the same provider tab.
- The Playwright fallback opens a fresh temporary page for every turn, so its continuous tool-session support is weaker than extension mode.

## Troubleshooting

### `extension_connected` is `false`

- Confirm that the extension is enabled.
- Click **Reload** for the extension on `chrome://extensions`.
- Confirm that the provider is listening on port `4319`.
- Check whether another provider process is already using the port.

### `Could not establish connection. Receiving end does not exist`

After the extension code is updated, an old ChatGPT tab may not contain the new content script. Reload the extension and the provider tab, then try again.

### `Composer did not retain the complete prompt`

ChatGPT may have replaced the editor during page hydration, or another extension may have modified the input box. Disable extensions that rewrite the ChatGPT page or composer, then try again.

### Codex stays on “Reconnecting”

Confirm that `npm start` is still running, then check:

```bash
curl http://127.0.0.1:4318/healthz
```

If long replies frequently time out, increase the wait time:

```bash
npm start -- --timeout 900
```

### The web models do not appear in Codex

Run:

```bash
npm run status
node src/cli.mjs install
```

Then restart Codex completely. The install command clears the local model-directory cache so that Codex fetches the augmented model list again.

## Why this is not an MCP tunnel

This project replaces the Codex model Responses provider; it does not add a remote MCP tool to the model. Both the Chrome extension and Node.js provider run locally, and tool requests ultimately return to Codex's existing local execution and permission system. No MCP broker or Secure MCP Tunnel is required.

## Official configuration reference

The official Codex configuration reference documents `openai_base_url`, `model_providers.<id>.base_url`, `requires_openai_auth`, retry and streaming timeouts, and the only supported `responses` wire protocol:

- [Codex Configuration Reference](https://developers.openai.com/codex/config-reference)

This project's configuration installer uses the user-level `openai_base_url` and never writes provider routing into repository-level configuration.
